# CipherChat v3 – nicht-interaktive FHE-Inferenz für Qwen2.5-0.5B auf einer RTX 5080

Stand: 24.11.2026. Code: `cipherchat/v3/`, `train_v3.py`, `server/app_v3.py`, `scripts/v3_*`.
Messdaten: `results/v3/`.

## 1. Kurzfassung
v3 ist die Referenzmessung für den **nicht-interaktiven** Weg. Der Client verschlüsselt pro Token einmal und
bekommt einen Ciphertext zurück. Der Server rechnet alle 24 Schichten von Qwen2.5-0.5B auf Ciphertexts, also auch
RMSNorm, Softmax (Power-Softmax mit oder ohne Division) und die Aktivierung. Dazwischen frischt er die Ciphertexts
per CKKS-Bootstrapping auf (PhantomFHE + NEXUS-CUDA). Das Gegenmodell ist SL in `cipherllm`: Dort rechnet der Client
die Nichtlinearitäten, das kostet 3 Roundtrips pro Schicht.

Ergebnisse (Variante `pos`; Details in Abschnitt 6–8):
- **CKKS-Parameter:**
  - N = 2¹⁶, 128 Bit, log QP = 1480 (h = 192), 10 Rechenebenen zwischen zwei Bootstraps.
  - Bootstrapping (1024 dünne Slots) dauert 159 ms auf der RTX 5080. Die Schlüssel belegen ~7 GB, die Spitze liegt bei ~8,5 GB.
- **Engine:**
  - Exakt geprüft in einer numpy-Slot-Simulation: relativer Fehler 10⁻⁸ über alle 24 Schichten, identisches Top-1-Token.
  - Auf der GPU nach 4 Schichten Kosinus > 0,999 und MSE ~2·10⁻⁴.
- **Zeit (ganzes Modell, gemessen):** 31 s pro Token (29,2 s GPU) auf einer RTX 5080.
  - Bootstrapping: 65 % (119 Bootstraps à 160 ms).
  - Matrizen: 22 % für Kodieren + Ct×Pt, dazu 6 % Rotationen.
  - Nichtlinearitäten: 4 %.
  - Attention: 3 %.
- **Genauigkeit (ganzes Modell, GPU):** Kosinus ≥ 0,999997 und MSE ≤ 6·10⁻⁵ gegenüber der float64-Referenz, Top-1-Token
  bei allen geprüften Token identisch. Das Ziel der Aufgabe (Kosinus > 0,99, MSE < 10⁻³) ist deutlich erfüllt.
- **Qualität** (WikiText-2-Test, 2000 Abschnitte, Kontext 128, Lehrer Perplexität 31,1):
  - mit Bereichsschutz: 42,2 (+35 %);
  - wie der Server rechnet: 44,6 auf 97 % der Abschnitte. Die übrigen 3,3 % eskalieren, weil die Aktivierung ihren
    Bereich verlässt (Anteil 10⁻⁵).
- **Division (`div16`):** mit Schutz das beste Modell (Perplexität 39,7). Ohne Schutz brechen alle Sequenzen, weil 0,4 %
  der Nenner das Newton-Fenster verlassen.
- **Wichtigste Erkenntnis:** Die Division der Power-Softmax (x^{2p}/Σx^{2p}) ist unter CKKS numerisch kaum machbar. Die
  Nenner streuen über 4–5 Größenordnungen, nach dem Bootstrapping bleiben aber nur ~17 Bit. Die divisionsfreie
  Variante (`norm = pos`) spart dazu 2 Bootstraps pro Schicht.

## 2. Architektur
```
Client                                   Server (GPU)                                   Client
token -> Embedding (öffentlich) -> Enc -> 24 x [RMSNorm, QKV, RoPE, Power-Attention,  -> Dec -> finale RMSNorm
                                          W_o, RMSNorm, Gate/Up, Quadrat-Akt., Down]          + LM-Head -> Token
                                          + Bootstrapping wenn nötig
```
- **Öffentliches Präfix `<|endoftext|>` + `\n` (Positionen 0–1):**
  - Der Server rechnet es im Klartext mit den exakten Operationen und legt seine K/V verschlüsselt in den Cache.
  - Grund (`scripts/v3_stats.py`): Mit nur einem Präfix-Token trägt Qwen2.5 bei ~20 % der Sequenzen auf dem ersten
    Nutzertoken „massive activations“ (mean(x²) bis 2600, Kanäle 62/490/570, Schichten 3–21). Das Max/Min-Verhältnis
    pro Norm liegt dann bei bis zu 4·10⁴.
  - Mit zwei Präfix-Token treten sie nur an Position 0 auf; das Verhältnis fällt auf ≤ 12.
- **Rollen:** `ClientV3` (Schlüssel, Ver- und Entschlüsseln, LM-Head) und `Engine3` (nur Ciphertexts) sind getrennte Klassen.
  Für die Demo laufen beide im selben GPU-Prozess, weil PhantomFHE Schlüssel nicht exportieren kann. Siehe Abschnitt 9.

## 3. Modell-Umbau (Klartext, `cipherchat/v3/model.py`, `approx.py`)
Alle Ersatzfunktionen stehen einmal in `approx.py`. Training, Referenz und Engine rechnen damit identisch, wie schon
in v1/v2.

| Original | v3 (Server, ab Position 2) | Tiefe |
|---|---|---|
| RMSNorm | m = Σx²/896 → y ≈ (m/m_ref)^{-1/2}: Startpolynom + Newton; 1/√m_ref und die Verstärkung g in W eingerechnet | Grad + 2·Iter. (kalibriert: Grad 1 + 4 Newton = 9) |
| Softmax | e_j = (α_h s_j + c_h)^{2p}, p = 2; `div`: e/Σe über Newton-Inverse; `pos`: e/((t+1)κ_h) | 3 (+ Inverse) |
| SiLU(gate)·up | (c₀ + c₁g + c₂g²)·up, Koeffizienten pro Neuron trainiert | 2 + 1 |
| RoPE | pro Position in W_q / W_k eingerechnet (Gewichte werden ohnehin pro Token kodiert) | 0 |
| Embedding, finale Norm, LM-Head | Client (öffentliche Gewichte) | – |

Training (`train_v3.py`):
- KD gegen das unveränderte Modell: KL auf den Logits + 0,1 × relativer Hidden-MSE + Bereichs-Strafterm.
- Daten: FineWeb-Edu, Kontext 128.
- Kurrikulum: Die Näherungen werden über 1000 Schritte eingeblendet.
- **Bereichsschutz:** Im Training greift außerhalb des kalibrierten Bereichs die exakte Operation. Ohne Schutz löst ein
  seltener Ausreißer eine Fehlerkaskade aus (NaN nach wenigen Schichten, siehe auch cipherllm RESULTS §2). Der Strafterm
  zieht die Werte in den Bereich. Ausgewertet wird **ohne** Schutz, also so, wie der Server rechnet.

## 4. CKKS-Parameter und Mikrobenchmarks (Meilenstein 1, `results/v3/m1_*.json`)
- **Modulkette:** 51 | 10 × 46 (Rechenebenen) | 14 × 51 (Bootstrapping) | 5 × 51 (Spezialprimzahlen) → log QP = 1480.
  - 128 Bit: Mit dünnem Geheimschlüssel (h = 192) liegt die Grenze bei 1546 (Lattigo N16QP1546H192).
  - Die NEXUS-Einstellung N = 2¹⁵ mit log QP ≈ 1550 ist **nicht** 128-Bit-sicher; sie war für den A100-Speicher gewählt.
- **Schlüsselgröße:** Fünf Spezialprimzahlen statt einer senken dnum von 25 auf 5. Pro Rotationsschlüssel 162 MB statt ~0,5 GB.
  Mit einer Spezialprimzahl scheitert der NEXUS-Benchmark auf 16 GB schon beim Schlüsselanlegen.

| Bootstrapping (N = 2¹⁶) | Zeit | max. Fehler | Phasen (CoeffToSlot / EvalMod / SlotToCoeff) | Schlüssel | VRAM-Spitze |
|---|---|---|---|---|---|
| 1024 Slots (logn 10) | 159 ms | 6·10⁻⁶ | 45 / 71 / 36 ms | 42 (6,8 GB) | 7,8 GB |
| 8192 Slots | 222 ms | 5·10⁻⁶ | 78 / 70 / 69 ms | 51 (8,1 GB) | 9,2 GB |
| 32768 Slots | 341 ms | 6·10⁻⁶ | – | 53 (8,0 GB) | 9,1 GB |

- **Genauigkeit nach Betrag der Eingabe** (`results/v3/boot_range.json`): relativer Fehler 7·10⁻⁶ bis |x| = 1,
  2·10⁻⁵ bei 2, 10⁻⁴ bei 4, 2·10⁻³ bei 16, 3 % bei 64.
  → Vor jedem Bootstrapping wird auf |x| ≤ 1 skaliert.
- **Kosten pro Operation**, Ebene 10 / Ebene 2:

  | Operation | Ebene 10 | Ebene 2 |
  |---|---|---|
  | Rotation | 0,39 ms | 0,11 ms |
  | Ct×Ct + Relin + Rescale | 0,49 ms | 0,15 ms |
  | Ct×Pt | 0,018 ms | 0,007 ms |
  | Kodieren eines Klartexts | 0,24 ms | 0,24 ms |

- **1024×1024-Matrix-Vektor-Produkt** (BSGS, Layout „offset → periodisch“): 25 ms, Fehler 10⁻⁷. Davon 18 ms Kodieren der
  32 Klartext-Diagonalen. Die Layout-Umwandlung periodisch → offset kostet 18 ms (13 davon Kodieren).

## 5. Engine (`cipherchat/v3/engine.py`)
- **Layouts:** n = 32768 Slots, Block D = 1024, R = 32 Kopien.
  - PER (periodisch): ein dünner CKKS-Vektor mit 1024 Slots. Alles, was gebootstrappt wird, ist PER oder ein replizierter
    Skalar, deshalb reicht **ein** Bootstrapper.
  - OFF (versetzt): Eingangslayout jeder Matrixmultiplikation.
  - KV-Cache: Slot j·128 + g·64 + d mit bis zu 256 Positionen.
  - q-Zeilen sind umsortiert zu o = m·128 + g·64 + d (Kopf h = 7g + m). So liegen die Kopfpaare der GQA-Gruppen auf dem Cache.
- **Matrix-Vektor:**
  - OFF → PER mit 32 Klartext-Diagonalen, 8 Baby- und 4 Giant-Schritten, dann Falten über 5 Rotationen.
  - FFN in 1024er-Blöcken: 10 Up/Gate-Blöcke mit gemeinsamen Baby-Rotationen, Down als Summe über 5 Blöcke mit einer Faltung.
- **Attention pro Kopfpaar m (7×):**
  1. q maskieren und über j replizieren (3 Rotationen).
  2. Ct×Ct mit dem K-Cache, Summe über d (6 Rotationen).
  3. (αs + c)⁴, über d verteilen (6 Rotationen).
  4. × V-Cache, Summe über j (8 Rotationen).

  Danach werden die 7 Ergebnisse mit Masken in einen PER-Ciphertext gepackt. Bei `div` folgen Nenner, Newton-Inverse und Produkt.
- **Newton:** Zwischenschritte von 1/√x halten Y = κy (κ = 2^k). So braucht der Newton-Schritt Y' = 3Y − (z/κ²)Y³ keine
  nicht-ganzzahlige Konstante. Der letzte Schritt liefert y/2 direkt ohne Extra-Ebene, damit y im Bootstrapping-Bereich liegt.
- **Bootstrapping-Skalierung:** Grenzen pro Schicht und Stelle, als Zweierpotenzen. Kalibriert mit der numpy-Simulation
  (`--save_bounds`, 1,5× Marge). Wo möglich steckt der Faktor gratis in der vorigen Klartext-Multiplikation (Packmasken,
  letzter Newton-Schritt). Zurückskaliert wird durch Verdoppeln, ohne Ebene.
  Globale Grenzen statt Grenzen pro Schicht machten die ersten Schichten ~10 % ungenau.
- **Skalar-Bootstrapping** (NEXUS-Pfad logn = 0, für die Norm-Faktoren y1/y2): 97 statt 160 ms, danach sogar 14 statt
  10 Ebenen. Der Fehler liegt aber bei 5·10⁻³ statt 7·10⁻⁶ bei |x| = 1 (`results/v3/boot_range.json`). Für den Faktor,
  der das ganze Residual skaliert, ist das zu grob, daher standardmäßig aus (`Engine3.scalar_boot`).
- **Rotationsschlüssel:** Die 35 Bootstrapping-Schlüssel plus 7 eigene, zusammen 42. Jede andere Verschiebung wird per
  BFS über Z_n aus diesen zusammengesetzt (`RotPlan`).
- **Ebenenplan pro Schicht** (`pos`; `div` braucht 2 Bootstraps mehr für Nenner und Zähler):
  x (Boot) → x² → Newton → y/2 (Boot) → q, kv = y·W x → Attention (Tiefe 7) → o (Boot) → W_o → x2 (Boot) → Norm → y2 (Boot)
  → Gate/Up → Aktivierung → Down → x3. Das sind 5 Bootstraps pro Schicht (`div`: 7).

## 6. Qualität (Meilenstein 2)
Messung (`results/v3/range_diag_pos.json`):
- Datensatz: WikiText-2-Test, 2000 Abschnitte à 126 Token hinter dem Präfix.
- Training: 6000 Schritte à 16 × 128 Token (12 M Token), ~50 min auf einer RTX 5080.

| Modell | Perplexität | kaputte Abschnitte |
|---|---|---|
| Qwen2.5-0.5B (Lehrer, exakt) | 31,1 | – |
| v3 `pos`, mit Bereichsschutz (exakte Op außerhalb des Bereichs) | 42,2 (+35 %) | 0 |
| v3 `pos`, ohne Schutz = was der Server rechnet | 44,6 (+43 %) | 65 / 2000 (3,3 %) |
| v3 `div16` (Division, Fenster Faktor 16), mit Bereichsschutz | 39,7 (+28 %) | 0 |
| v3 `div16`, ohne Schutz = was der Server rechnet | – | **2000 / 2000 (100 %)** |

Außerhalb des kalibrierten Bereichs:
- RMSNorm: 6·10⁻⁷ der Werte, höchstens 1,26-fach.
- Aktivierung: 10⁻⁵ der Werte, höchstens 3-fach.
- Attention (`pos`): nie.

Die kaputten Abschnitte entstehen, wenn das Quadratpolynom der Aktivierung an einem solchen Ausreißer extrapoliert. Der
Fehler pflanzt sich über die Attention in die ganze Sequenz fort. Gegenmittel (offen):
- Polynom auf einem breiteren Bereich anpassen;
- Strafterm höher gewichten;
- Klipp-Polynom vor der Aktivierung (kostet 2–3 Ebenen).

Zwischenstände der `div`-Läufe:
- Erster `div`-Lauf mit Quantil-Bereich: Schritt 2000 Perplexität 46,4 (Lehrer 29,3).
- Beim Umschalten auf die Newton-Inverse (Schritt 2400) lag der Nennerbereich bei [0,01; 418]. Keine Newton-Variante mit
  Tiefe ≤ 12 erreicht dort weniger als 99 % Fehler → Lauf abgebrochen.
- `div16` zwingt den Nenner in ein Fenster mit Faktor 16 um den Median, [0,23; 3,7]. Dort schafft Grad 3 + 3 Newton
  (Tiefe 9) einen Fehler von 3·10⁻⁴.
  - Mit Schutz ist das Modell das beste (39,7). Aber 0,4 % der Nenner liegen weiterhin außerhalb des Fensters, bis zu
    470-fach (`results/v3/range_diag_div16_attn300.json`).
  - Ohne Schutz divergiert die Newton-Inverse dort, und **jede** Sequenz bricht.
  - Der Strafterm (Gewicht 1) hat das Modell nicht ins Fenster gedrückt, und der Schutz im Training hat das verdeckt.
  - Folgerung: Die Division taugt unter CKKS nur, wenn der Nenner per Konstruktion beschränkt ist. Beispiele: ein
    additiver Senken-Term (Σe + κ) zusammen mit beschränkten Scores, oder ein deutlich stärkerer Strafterm, dessen
    Ergebnis ohne Schutz geprüft wird. Die divisionsfreie Variante `pos` ist der praktikable Weg.

| Hotspot pro Token | ms | Anteil |
|---|---|---|
| 1 Lineare Projektionen: Kodieren + Ct×Pt | 6510 | 22,3 % |
| 1 Lineare Projektionen: Rotationen | 1642 | 5,6 % |
| 2 Attention: Ct×Ct, Cache, Packen | 282 | 1,0 % |
| 2 Attention: Rotationen | 542 | 1,9 % |
| 3 Nichtlinear: Norm, Softmax, Aktivierung | 1164 | 4,0 % |
| 4 Bootstrapping (119×) | 19072 | 65,3 % |
| **Summe GPU** | **29213** | |

- **Zeit:** 30,8–33,0 s pro Token (wall), Python-Anteil ~1,7 s. Bootstrapping-Phasen pro Token: CoeffToSlot 5,3 s,
  EvalMod 8,6 s, SlotToCoeff 4,3 s, Subsum 0,6 s.
- **Genauigkeit** des finalen Residuals gegenüber der float64-Referenz: Kosinus 0,999997–0,999999, relativer Fehler
  1,5–2,7·10⁻³, MSE 2–6·10⁻⁵. Top-1 an allen 4 Positionen identisch: „ answer“, „ of“, „ the“, „ is“.
- **Operationen pro Token** (numpy-Zählung): 119 Bootstraps, 11 048 Rotationen, 21 095 Ct×Pt, 1 824 Ct×Ct.
- **Schlüsselerzeugung:** 21 s.

**Einordnung:**
- THOR braucht für BERT-base (110 M, 128 Token, Encoder) ~10 min auf einer A100. v3 dekodiert ein 0,5B-Modell mit
  ~31 s pro Token auf einer 16-GB-Consumer-Karte. Der Vergleich ist nur grob, weil Aufgabe und Packing verschieden sind.
- Gegenüber SL (cipherllm, GPT-2: ~1 Token/s mit Client-Roundtrips) kostet die Nicht-Interaktivität Faktor ~30 in der
  Latenz. Dafür braucht es nur einen Roundtrip pro Token und keinerlei Client-Rechnung.

**Hebel für die nächste Stufe** (geschätzt):
- 2 der 5 Bootstraps pro Schicht entfallen, wenn die RMSNorm flacher wird: −26 %. Möglich mit schmalerem Bereich oder
  einem genaueren logn = 0-Bootstrapper.
- Weights direkt auf der GPU kodieren statt Host→GPU-FFT: −15 %.
- Hoisting der Baby-Rotationen: −3 %.
- Batching mehrerer Nutzer: Heute trägt jeder Ciphertext nur 896 Nutzwerte in 32 768 Slots (Kopien für das BSGS-Layout). Ein Layout für mehrere Nutzer würde den Durchsatz pro GPU vervielfachen.

## 9. Grenzen und offene Punkte
- **Schlüsselübergabe:** PhantomFHE (NEXUS-Fork) kann Schlüssel und Ciphertexts nicht serialisieren. Im Demo-Server
  liegen Client-Schlüssel und Engine im selben Prozess. Eine echte Trennung braucht den Export von ~7 GB
  Auswertungsschlüsseln, als Seeds halbiert (~3,5 GB).
- **Lizenz:** NEXUS ist GPL-3.0. Der Code wird nur beim Bauen geholt (`scripts/v3_setup_remote.sh`) und nicht ins Repo
  übernommen. Für ein Produkt braucht es eine eigene Bootstrapping-Implementierung oder eine andere Lizenz.
- **Sicherheit:** Die Grenze log QP ≤ 1546 für h = 192 folgt Lattigos Parametersatz. Eine eigene Prüfung mit dem
  Lattice-Estimator steht aus.
- **Kontext:** maximal 256 Positionen (KV-Layout). Der Prompt läuft Token für Token (wie Dekodieren), jedes Token kostet die volle Zeit.

```bash
bash scripts/v3_sync.sh at-10-1-4 && ssh at-10-1-4 'cd ~/cipherchat && bash scripts/v3_setup_remote.sh'   # NTL, NEXUS, Build
build_v3/v3_bench_m1 cipherchat/v3/config.json "bench.logn_boot=[10]"                                   # Meilenstein 1
python scripts/v3_stats.py                                                                              # Ausreißer-Statistik
python train_v3.py --name q05_pos --norm pos --steps 6000                                               # Meilenstein 2
python scripts/v3_range_diag.py --ckpt weights/v3/q05_pos.pt                                            # FHE-Perplexität ohne Schutz
python scripts/v3_check.py --ckpt weights/v3/q05_pos.pt --backend numpy --tokens 4 --save_bounds weights/v3/q05_pos_bounds.json
PYTHONPATH=build_v3 python scripts/v3_check.py --ckpt weights/v3/q05_pos.pt --backend phantom --tokens 3 \
    --bounds weights/v3/q05_pos_bounds.json --out results/v3/check_phantom_pos.json                     # Meilenstein 3/4
V3_CKPT=weights/v3/q05_pos.pt bash run_demo_all.sh                                                      # UI mit v1/v2/v3
```
